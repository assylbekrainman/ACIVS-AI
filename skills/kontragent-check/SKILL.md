# Проверка контрагентов и договора на риски и аффилированность

Самостоятельный скилл ДКТ АО «Фонд науки». Эскроу-скиллы (`escrow-payment-forte`, `escrow-payment-alatau`, `escrow-fot`) НЕ вызывает и НЕ меняет — работает отдельно. Используй, когда пользователь просит:
«проверь контрагента / поставщика / БИН», «проверь договор на риски и аффилированность», «проверь КП на аффилированность», «прогони через КГД», «проверка по всем базам», присылает ссылки ba.prg.kz / kompra.kz / adata.kz или справку egov о регистрационных действиях.

Результат — всегда файл: заключение `.docx` (формат ниже) + `kgd_final.txt` с полным выводом анализатора, сохранённые рядом с проверяемым договором на компьютере пользователя.

## Инструменты (набор на компьютере пользователя)

Папка: `C:\Users\Фонд науки\Desktop\Postman\kontragent_check\`
(токен КГД лежит уровнем выше: `Desktop\Postman\токен.docx`)

| Файл | Назначение |
|---|---|
| `run_kgd_check.bat` / `run_kgd_check.ps1` | Запрос в API КГД по БИН из `bins.txt`. PowerShell, Python на компьютере НЕ нужен (его там нет). Результат: `kgd_raw\<БИН>.json`, `kgd_report.txt` |
| `bins.txt` | Список БИН, по одному в строке (перезаписывает Claude) |
| `check_counterparty_kgd.py` | Анализатор: валидация БИН/ИИК, флаги КГД, граф аффилированности, команда ГП. Запускается в облачном контейнере Claude |
| `counterparties.template.json` | Шаблон нормализованных данных |

API КГД: `POST https://portal.kgd.gov.kz/services/isnaportal/public/get-sur-data`, заголовок `X-Portal-Token`, тело `{"xin":"<БИН>"}`. Коды: 400 — формат БИН, 401 — токен, 404 — токен не активирован, 500 — сервер КГД.

**Ограничения среды (проверено):**
- Облачный контейнер и `device_bash` на компьютере пользователя НЕ достают `portal.kgd.gov.kz`, `goszakup.gov.kz`, `kompra.kz`, `data.egov.kz` (allowlist прокси). `WebFetch` достаёт `ba.prg.kz`.
- Запустить `.bat` через computer use нельзя: Проводник выдаётся в режиме «клик», двойной щелчок не запускает файл. **Запуск `run_kgd_check.bat` делает пользователь двойным щелчком** — попроси одним сообщением и жди «готово».
- Токен КГД не вводи никуда сам (ни в браузер, ни в поля, ни в `.env` через удалённые инструменты — запись `.env` запрещена). Скрипт находит токен сам в `токен.docx`.
- Портал КГД в браузере закрыт reCAPTCHA — не обходить.

## Порядок работы

Создай task list по шагам 1–7.

### 1. Собери исходные данные
- Договор (стороны, БИН, реквизиты, предмет, цена, график оплаты, сроки, обеспечение).
- Список ВСЕХ проверяемых юрлиц: поставщик; участники сравнения КП (альтернативные поставщики — из письма ГП, протокола выбора, сметы/заявки); сам ГП; частный партнёр/софинансирующая сторона. Если КП-участники неизвестны — спроси.
- Команда ГП (для `--team`): руководитель проекта, члены проектной группы (лист «1 ФОТ» сметы / заявка), директор ГП, директор частного партнёра.
- Документы проекта в claude.ai Project (если подключён): смета (лист «2 Обор.» — кто определён поставщиком, КП и цены), договор гранта (п. о закупе: ≥3 КП, неаффилированность с ГП и **друг с другом**, не в реестре недобросовестных), календарный план, КПЭ.

### 2. Открытые реестры — по каждому БИН
- `WebFetch https://ba.prg.kz/000000000-unknown/<БИН>-<БИН>/` (формат URL работает для любого БИН): руководитель, учредители, адрес, ОКЭД, КРП, налоги по годам, НДС, риски, **«Смежные предприятия»** с типом связи и контакты (телефон, e-mail).
- Для каждого «смежного предприятия» — тоже карточка (связанные лица часто и дают цепочку: общий директор → e-mail с фамилией директора третьей фирмы → общий адрес).
- Справка egov о регистрационных действиях (если пользователь приложил PDF) — первичный источник по учредителю/руководителю/адресу/истории.
- kompra.kz / adata.kz / goszakup.gov.kz (реестр недобросовестных) / sud.gov.kz — `WebFetch`/`WebSearch`; если недоступно — прямо пометить «не проверено» в отчёте, не выдавать за пройденное.

### 3. API КГД
1. Запиши список БИН в `bins.txt` на компьютере:
   `device_bash`: `printf '%s\r\n' 170440028314 141040006475 > "$HOME/mnt/Postman/kontragent_check/bins.txt"` (папка `Desktop\Postman` должна быть подключена; если нет — `device_request_folder_access` на неё).
2. Попроси пользователя: «Дважды щёлкните `run_kgd_check.bat` в Desktop\Postman\kontragent_check и напишите «готово»».
3. Прочитай `kgd_report.txt` (`device_bash cat`) и забери `kgd_raw\*.json` через `device_stage_files` в контейнер.
4. Ошибка 401/404 — токен (попроси проверить/обновить `токен.docx`); `Python` в отчёте — значит запущен старый батник.

Что даёт КГД: наименование, ОКЭД, режим, НДС, задолженность; флаги bankrupt / inactive / registrationInvalid / reRegistrationInvalid / operationsWOWork / esfRestrinctions / regAddressAbsent / courtDecisionRegistry / selfRegulatoryRegistry («Нет данных» = записи нет); статистика по годам: workersCount, taxIn, КНН и среднеотраслевой КНН.
Чего КГД НЕ даёт: руководитель, учредители, адрес, контакты, перечень неблагонадёжных — это из шага 2.

### 4. Анализатор
1. Скопируй `check_counterparty_kgd.py` с компьютера в контейнер (`device_stage_files`).
2. Собери `counterparties.json` по шаблону: все юрлица из шагов 2–3, `team`, для поставщика — `accounts` (ИИК) и `expected_oked_prefixes` по предмету закупа (оборудование: 28, 4669, 4663, 4614, 3312, 3320; услуги — по профилю). Неизвестные флаги — `null` (будут GAP), не `false`.
3. `python3 check_counterparty_kgd.py --from-json counterparties.json --compare --kgd-raw-dir <папка kgd_raw> --json-out kgd_final.json > kgd_final.txt`
   Код выхода 1 = есть красные флаги или связи.
4. Анализатор ищет связи: общее лицо (директор/учредитель/бывший директор), совпадение юр./факт. адреса (разные написания), общий телефон/e-mail, e-mail с фамилией руководителя другой фирмы (с транслитом), идентичный набор ОКЭД, «смежные» во внешнем источнике, совпадения с командой ГП (полное ФИО — RED, фамилия — AMBER).
5. Дополнительно (read-only, если есть): внутренний реестр проектных команд 2022–2025 — `check_affiliation.py` из пакета эскроу-скиллов можно только ЗАПУСКАТЬ, не редактировать.

Если набор на компьютере недоступен — выполни те же сравнения вручную по этим правилам и укажи это в отчёте.

### 5. Проверка договора — чек-лист рисков
Сверь с договором гранта, сметой и календарным планом; по каждому пункту — риск, уровень (Критично/Высокий/Средний/Низкий) и готовая редакция:
- Поставщик = определённый в смете? Если сменён — протокол выбора и 3 КП есть? Цены совпадают с КП другого юрлица «до тенге» — признак подгонки под смету.
- Позиции/модели/количество спецификации vs смета; производитель, страна, характеристики указаны?
- Размер аванса и предоплаты; поставка после 100% оплаты; обеспечение (банковская гарантия возврата аванса).
- Сроки поставки vs календарный план (монтаж, ПНР, обучение, доход по КПЭ).
- Условия траншей ссылаются на существующие обязанности (отчёт поставщика и т.п.).
- Счёт списания: эскроу-счёт (грант) и счёт софинансирования, а не текущий счёт ГП; порядок разрешения Фонда.
- Монтаж/шеф-монтаж/ПНР в цене (смета обычно требует «поставка, монтаж и ПНР входят в стоимость»).
- Неустойки и лимиты vs объём аванса; основания одностороннего отказа (включая выявленную аффилированность, требование Фонда).
- Конфиденциальность — исключение для Фонда, НЦГНТЭ, ВАП, госорганов.
- Заверение поставщика об отсутствии аффилированности; маркировка логотипом Фонда.
- Реквизиты: БИН (mod 11), ИИК (mod 97, латиница, 20 знаков), БИК ↔ банк, пустые поля; нумерация разделов и перекрёстные ссылки; опечатки.
- Профиль поставщика: ОКЭД vs предмет, численность по КГД, налоги vs цена договора, адрес — квартира.
- Отдельно: способность частного партнёра внести софинансирование (численность/налоги по КГД).

### 6. Заключение .docx
Прочитай `docx` скилл (SKILL.md) и собери документ (A4, Arial, цветовая маркировка ячеек: красный/янтарный/зелёный/серый):
1. Шапка + плашка «ВЫВОД» (рекомендовать / не рекомендовать к согласованию и оплате, 2–3 блокера).
2. Параметры сделки и сверка со сметой (таблица).
3. Аффилированность: таблица «Связь — Факт — Источник» + оценка по п. о закупе договора гранта.
4. Профиль поставщика + сводка API КГД по всем лицам (работники и налоги по годам, вывод).
5. Риски условий договора с рекомендуемыми редакциями.
6. Технические/редакционные замечания.
7. Что не проверено и почему.
8. Рекомендуемые действия (письмо ГП: протокол выбора, 3 КП, справки egov об учредителях участников КП, подтверждение софинансирования).
9. Источники (URL карточек, дата актуальности КГД).
Проверь рендер (`soffice` → `pdftoppm`), затем `device_commit_files` рядом с договором и `SendUserFile`.

### 7. Итог в чате
Коротко: вывод, 3 главных факта с цифрами, что осталось открытым, где лежат файлы. Не выдавать совпадение ФИО без второго подтверждения за доказанную аффилированность — формулировка «признаки аффилированности», вывод делает менеджер.
