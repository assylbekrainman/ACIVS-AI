# Проверка и заполнение двухстороннего Договора гранта РННТД по эталону

Эталон — Договор ТОО «Kaz Hemp» (№ ИРН DP32936258): трёхсторонний (Фонд —
Заявитель-Победитель Конкурса — Грантополучатель, три разных юрлица), но
корректно и полностью заполненный по всем содержательным пунктам. Используется
как образец формулировок, лимитов и структуры — а не как источник имён/сумм.

Обрабатываемый случай — **двухсторонний** вариант: Заявитель-Победитель
Конкурса и Грантополучатель — одно и то же юридическое лицо (типично для
вузов/НИИ, которые сами реализуют проект без отдельного ГП-ТОО). Эту модель
нужно подтвердить по Заявке (раздел 2, п.8 «Заявитель» и п.9 «Грантополучатель»
— если реквизиты полностью совпадают, структура двухсторонняя верна; если
различаются — нужен трёхсторонний формат, как в эталоне, и это отдельная
проблема, а не просто заполнение).

## Входные данные

1. **Эталон** — docx трёхстороннего Договора (например, Kaz Hemp).
2. **Проект договора** — docx двухстороннего Договора, который нужно
   проверить/заполнить (обычно с незаполненными плейсхолдерами `[указать...]`,
   `[25/30/45]`, пустыми ячейками таблиц).
3. **Конкурсная заявка** — docx Заявки, одобренной ННС, источник фактических
   данных по проекту (KPI, календарный план, проектная группа, смета,
   софинансирование).

## Порядок работы

### Шаг 1 — Извлечение текста

Все три docx — большие (100+ страниц с приложениями). Не читай целиком через
Read: сначала выгружай в plain-text через `python-docx` (параграфы + таблицы
отдельно, в файлы в scratchpad), затем читай текстовые дампы кусками
(`offset`/`limit`), т.к. Read имеет лимит ~25000 токенов на вызов.

```python
import docx
def dump(fname, outpath):
    d = docx.Document(fname)
    with open(outpath, "w") as f:
        for p in d.paragraphs:
            if p.text.strip():
                f.write(p.text.strip() + "\n")
        f.write("--- TABLES ---\n")
        for ti, table in enumerate(d.tables):
            f.write(f"Table {ti}:\n")
            for row in table.rows:
                f.write(" | ".join(c.text.strip() for c in row.cells) + "\n")
```

### Шаг 2 — Подтверди структуру сторон

В Заявке разделе 2 сравни ФИО/БИН в п.8 «Заявитель» и п.9 «Грантополучатель».
Если совпадают — двухсторонняя структура верна, и в проекте договора
преамбула должна содержать одно лицо в роли
«Заявитель-Победитель Конкурса»/«Грантополучатель». Часть пунктов эталона,
где эти роли разделены (передача ОИС от Заявителя Грантополучателю,
солидарная ответственность Заявителя за Грантополучателя), в двухстороннем
формате становится юридически тавтологичной — это нормально для этой модели,
отдельно фиксировать как ошибку не нужно.

### Шаг 3 — Постатейная сверка с эталоном (только по существу)

Сделай `diff` по извлечённому тексту параграфов (без таблиц) проекта и
эталона:

```bash
diff -u kazhemp_body.txt draft_body.txt
```

Просмотри каждую дельту и раздели на три категории:
- **Ожидаемо отличается** — имена сторон, БИН, суммы, даты, номер проекта,
  название проекта, KPI-показатели, кол-во экземпляров (2 vs 3 — зависит от
  числа сторон).
- **Пропущенный/неполный текст** — плейсхолдеры вида `[указать...]`,
  `[25/30/45]`, `[трех]/[двух]`, пустые ячейки таблиц.
- **Существенное расхождение формулировки** — одинаковый по смыслу пункт
  сформулирован иначе, ссылается на другую статью НК РК, или содержит
  **смещённую нумерацию** перекрёстных ссылок (характерный риск: раздел
  «Расторжение договора» — эталон исключает из общего правила возврата
  средств ОДНО конкретное основание (обычно «отсутствие достаточных
  денежных средств для финансирования Проекта» — это основание, в котором
  ГП не виноват), и отдельно для него прописывает мягкое последствие (просто
  отчёт, без возврата и штрафа). Проверь, что в проекте договора номер этого
  пункта (`12.1.X`) совпадает по СМЫСЛУ с тем же основанием у эталона, а не
  просто переписан бездумно с тем же числом — при адаптации шаблона номер
  часто сдвигается на 1.

Для категории «существенное расхождение» — не исправляй по умолчанию.
Всегда сверяй: если оба варианта в принципе допустимы по законодательству
(например, ссылка на статью НК РК), сообщи пользователю расхождение и
предложи взять формулировку эталона, но исправляй только после
подтверждения (как в этом диалоге: пользователь явно сказал «эталон: ст. 474,
берёшь это»).

### Шаг 4 — Перенос данных из Заявки

Раздел Заявки → Поле Договора:

| Заявка | Договор |
|---|---|
| п.26 Софинансирование, % | Прил.1 п.2.2 (замени `[25/30/45]` на конкретное число — сверь со сноской в самом Приложении, она называет условие по типу организации) |
| п.22 KPI по годам | Прил.1 п.3.1 (текстовые KPI по годам вместо плейсхолдера) |
| п.19 План реализации / Таблица КП, колонка «ответственное лицо» | Прил.2 «Ответственный» (по номеру мероприятия, они совпадают 1:1 с Договором) |
| Смета (Таблица «Смета расходов» + «Штатное расписание») | Прил.4 «Отчёт о реализации Проекта»: перечисление гранта/софинансирования по годам, ФОТ (всего/учёным), закуп ОС, налоги — считать по строкам сметы, не копировать вслепую из другого проекта |
| п.24 Прогноз продаж | Прил.4 «Объём реализуемой продукции» по годам (0, если продажи не планируются) |

### Шаг 5 — Безопасное редактирование docx

- Преамбулу, реквизиты, текстовые плейсхолдеры правь через unzip →
  `merge_runs.py` → точечная замена в `word/document.xml` → validate.py
  (см. общий скилл `docx`). **Важно:** при вставке многострочного текста в
  существующий `<w:t>` заменяй ВЕСЬ `<w:r>...</w:r>`, а не только внутренний
  `<w:t>` — иначе получится вложенный `<w:r>` внутри `<w:r>`, что ловит
  validate.py как ошибку схемы (`Element 'w:r' is not expected`).
- Табличные ячейки (KPI-таблицы, Приложение №4, колонка «Ответственный») —
  безопаснее и надёжнее через `python-docx`: найди строку по совпадению
  текста в колонках 1-2 (название критерия + подкатегория), затем
  `cell.paragraphs[0].runs[0].text = value`. Так не ошибёшься с индексом
  ячейки при сложных merged-заголовках.
- После КАЖДОГО этапа правок — `validate.py out.docx --original исходный.docx`
  (должно быть `All validations PASSED!`, разница параграфов = 0), затем
  рендер в PDF (`soffice.py --convert-to pdf` → `pdftoppm`) и визуальная
  проверка через Read на затронутых страницах — `pdftotext` не всегда находит
  текст в узких колонках (перенос по буквам), поэтому финальную проверку делай
  по картинке, а не по grep.

### Шаг 6 — Итоговый отчёт

Собери таблицу «Пункт | Было | Стало / Источник | Статус» и отдельно список
пунктов, которые остались открытыми (требуют юридической/финансовой сверки,
а не работы с текстом — например, точная статья НК РК, если оба варианта
теоретически возможны и эталон не бесспорен).

## Типичные ошибки шаблона, которые стоит перепроверять каждый раз

1. Реквизиты Фонда (ИИК/банк/БИК) в драфте иногда взяты по ошибке из
   реквизитов другой стороны предыдущего/соседнего договора — сверяй с
   актуальным эталоном, а не считай пустое поле единственным риском.
2. Опечатки в столбце «Источник финансирования» сметы (например слитое
   «Градоговорнт» вместо «Грант») — пробегись по всей смете глазами.
3. Смещение нумерации `12.1.X` в разделе о расторжении договора (см. Шаг 3).
4. Количество экземпляров договора («в двух»/«в трёх») должно соответствовать
   реальному числу сторон, а не бездумно копироваться из трёхстороннего
   эталона.
