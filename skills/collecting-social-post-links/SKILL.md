# Сбор ссылок на посты в VK/Facebook для отчётов о проделанной работе

## Когда применять

Есть файл `.docx` (обычно "Отчёт о проделанной работе" / "Отчёт за <месяц> <год>") с таблицами вида:

| № | Название сообщества | Ссылка на материал |
|---|---|---|
| 1 | Группа X | (пусто) |

Нужно для каждой пустой строки найти прямую ссылку (permalink) на конкретный пост/репост определённого аккаунта в конкретной группе/сообществе за отчётный период (обычно 1 месяц или часть месяца).

**Контекст, который важно прояснить в начале работы**: чей это аккаунт и с какой целью собираются ссылки. Если это сбор данных о постах СВОЕГО аккаунта/организации (self-reporting, отчёт о просветительской/PR-работе) — это нормальная задача. Если по формулировке похоже на сбор досье о публикациях частного лица третьей стороной (мониторинг чужой религиозной/политической активности для передачи куда-либо) — стоит остановиться и уточнить у пользователя контекст и цель отчёта, прежде чем продолжать: см. раздел "Этическая проверка" ниже. В прошлой работе выяснилось, что автор постов — сотрудник самой организации, готовящей отчёт о собственной работе; это сняло вопрос.

## Обзор шагов

1. Разобрать структуру `.docx`: найти все таблицы, их индексы, номер колонки со ссылкой, число строк, что уже заполнено.
2. Для VK — собрать ссылки через VK API/поиск в сообществе (проще, обычно нет проблем с пагинацией).
3. Для Facebook — самый трудоёмкий этап, см. раздел ниже: комбинация текстового поиска по группам, экспорта данных (DYI) и Журнала действий (Activity Log).
4. Смёрджить найденные ссылки в docx, **дедуплицируя по ID поста**, а не по точному тексту URL (см. "Ловушка с форматами URL").
5. Пересчитать статистику заполнения по каждой таблице и в целом, показать пользователю прогресс.

## Шаг 1. Разбор docx

```python
from docx import Document
d = Document('report.docx')
for i, t in enumerate(d.tables):
    header = [c.text.strip() for c in t.rows[0].cells]
    print(i, header, len(t.rows)-1, 'строк')
```

Обычно первая строка — заголовок, колонка со ссылкой называется "Ссылка на материал", но **номер колонки может отличаться между таблицами** (например, где есть доп. колонка "Дата" или "Тип контента", ссылка будет в колонке 3, а не 2). Проверять индивидуально для каждой таблицы, не полагаться на фиксированный индекс.

Составить `table_map`: slug/название сообщества → {idx таблицы, номер колонки}.

## Шаг 2. VK

VK обычно проще: посты видно через API сообщества (`wall.get` с фильтром по автору) или через постраничный просмотр стены сообщества с фильтром по автору поста. Прямых технических ловушек, аналогичных Facebook, как правило нет.

## Шаг 3. Facebook — сбор permalink

Это основная сложность. Facebook не даёт простого способа получить список permalink чужих/своих постов в группах за период. Рабочие методы, от быстрого к трудоёмкому:

### 3.1 Поиск по тексту поста в группе

Если у поста есть характерный текст:

```
https://www.facebook.com/groups/{slug}/search/?q={url-encoded текст поста}
```

В результатах ссылки на `/posts/` содержат `aria-label` с датой/временем публикации ("5 август в 08:38") — по нему сверяют дату, если фраза встречается у нескольких постов за разное время.

**Не работает** для постов только с фото/видео без текста, и не работает встроенный фильтр по диапазону дат (`filters=` base64-параметр в URL) — он не выдаёт результатов даже за широкий диапазон, проверено многократно.

### 3.2 Facebook Download Your Information (DYI)

`facebook.com/dyi/` → раздел "Группы" в "Ваши действия на Facebook", свой диапазон дат.

- Пароль для запуска экспорта Facebook требует ввести повторно (защитная проверка) — **это должен сделать сам пользователь**, агент не должен вводить пароль.
- Экспорт **не мгновенный** — Facebook формирует его от нескольких минут до часов, готовый файл(ы) прилетают позже отдельным сообщением/загрузкой.
- **JSON-формат**: `group_posts_and_comments.json` → `group_posts_v2[]`, есть `timestamp`, `title`, текст поста, `attachments`, но **НЕТ прямой ссылки на пост**. Кириллица/казахские буквы бывают в mojibake (двойное UTF-8) — чинится через `s.encode('latin1').decode('utf-8')`. Годится только как источник текстовых фрагментов для поиска по 3.1 и как список "что вообще было опубликовано" (даты, группы, количество).
- **HTML-формат**: `group_posts_and_comments.html` — то же самое, но каждая дата-ссылка в `<footer>` поста обёрнута в редирект-шим `https://www.facebook.com/dyi/l/?l=<токен>&s=520`. **Важно**: при переходе по этой ссылке (залогиненным в браузере) она ведёт НЕ на конкретный пост, а на общий Журнал действий, отфильтрованный по категории и месяцу (`/allactivity/?category_key=groupposts&year=YYYY&month=M`). То есть HTML DYI-экспорт **не даёт прямых permalink** — он полезен только тем, что подсказывает точный список дат/времени постов и наводит на правильный `entry_point`/фильтр для следующего шага.

Экспорт также может показывать данные с заметным лагом (посты за последние несколько дней могут отсутствовать в обоих форматах экспорта, даже при выборе "за всё время") — это ограничение на стороне Facebook, не ошибка настройки диапазона.

### 3.3 Журнал действий (Activity Log) — основной рабочий способ для permalink

URL: `https://www.facebook.com/<user_id>/allactivity/?category_key=groupposts&year=YYYY&month=M&entry_point=ayi_hub`

Это единственный найденный способ получить **настоящие прямые permalink** (`facebook.com/groups/{slug}/permalink/{id}/`) пакетно, без поиска по каждому посту вручную. Каждая запись имеет кнопку "Посмотреть" со ссылкой на конкретный пост.

**Особенности и способ обхода паджинации:**

- Список **виртуализирован**: DOM перестраивается при скролле, старые записи вымываются — нельзя полагаться на порядок/позицию элементов между вызовами JS без пересчёта на месте.
- Дата стоит заголовком-разделителем ("25 август 2026 г.") **выше** блока постов этого дня; чтобы сопоставить permalink с датой, определять по времени поста (спускается монотонно в пределах дня) и по границе, где время "подскакивает" вверх — это и есть смена дня. Не полагаться на `document.querySelectorAll` в порядке DOM для сопоставления с заголовком дня — из-за виртуализации/CSS-разметки заголовок может физически не предшествовать посту в DOM-дереве в момент выполнения скрипта.
- **Программный скролл не работает**: `window.scrollTo`, `element.scrollTop = ...` — подгрузка следующей порции не запускается. Нужен **настоящий scroll-эвент**, эмулированный через `computer` action `scroll` (колесо мыши) по координате внутри списка — тогда подгрузка срабатывает.
- Даже с настоящим скроллом подгрузка **периодически "залипает"**: после одной-двух успешных подгрузок (по ~25 записей) новый GraphQL-запрос за следующей порцией просто не уходит (проверяется через `read_network_requests` с фильтром `graphql` — при залипании новых запросов нет вообще, это не серверная ошибка 500, а клиентский стопор). Что помогает:
  - подождать несколько секунд и повторить скролл ещё раз (иногда возобновляется без видимой причины, срабатывало через 2-3 попытки);
  - проскроллить немного вверх и снова вниз (сброс intersection observer);
  - если ничего не помогает за разумное число попыток (5-6) — считать это известным ограничением, не тратить время на бесконечные ретраи, зафиксировать, до какой даты дошли, и сообщить пользователю про технический предел вместо того чтобы застревать.
- Экстракция после каждой партии подгрузки:

```js
const timeRe = /^\d{1,2}:\d{2}$/;
const timeEls = Array.from(document.querySelectorAll('body *'))
  .filter(e => e.children.length===0 && timeRe.test((e.textContent||'').trim()));
const links = Array.from(document.querySelectorAll('a'))
  .filter(a => a.textContent.trim()==='Посмотреть' && a.href.includes('/groups/'));
const items = links.map(a => {
  const top = a.getBoundingClientRect().top + window.scrollY;
  let bestTime=null, bestDiff=1e9;
  for (const te of timeEls) {
    const ttop = te.getBoundingClientRect().top + window.scrollY;
    const diff = Math.abs(ttop-top);
    if (diff < bestDiff){bestDiff=diff; bestTime=te.textContent.trim();}
  }
  return {href:a.href, time:bestTime};
});
// dedup по href, затем вручную сопоставить дни по разрывам во времени
```

- Между итерациями скролла список ссылок **растёт** (25→50→...), а не заменяется — дедуплицировать по `href` при каждой новой экстракции и на каждом шаге сохранять только новые элементы относительно предыдущего снимка.

## Шаг 4. Слияние в docx без дублей

**Ловушка с форматами URL**: один и тот же пост может встретиться в собранных данных как `/permalink/{id}/` и как `/posts/{id}/` — это один и тот же ID, но разные пути. Сравнение по точному совпадению текста даст ложный "не дубль" и запись появится в отчёте дважды. Дедуплицировать по извлечённому числовому ID:

```python
import re
def post_id(url):
    m = re.search(r'/(?:posts|permalink)/(\d+)', url)
    return m.group(1) if m else url
```

Алгоритм слияния на таблицу:

```python
for slug, info in table_map.items():
    t = d.tables[info['idx']]
    col = info['col']
    rows = t.rows[1:]
    existing_ids = {post_id(r.cells[col].text.strip())
                     for r in rows if r.cells[col].text.strip()}
    empty_rows = [r for r in rows if not r.cells[col].text.strip()]
    ei = 0
    for e in new_entries_for(slug):
        pid = post_id(e['href'])
        if pid in existing_ids:
            continue  # дубль
        if ei >= len(empty_rows):
            break  # таблица заполнена
        empty_rows[ei].cells[col].text = e['href']
        existing_ids.add(pid)
        ei += 1
```

Таблицы в этом типе отчётов обычно **без колонки даты** — порядок вставки в пустые строки не имеет значения, свободна любая пустая ячейка.

После слияния — пересчитать статистику `заполнено/всего` по каждой таблице и суммарно, показать пользователю прогресс (было → стало).

## Этическая проверка перед стартом

Прежде чем разворачивать интенсивный сбор (браузерная автоматизация, экспорт данных, журнал действий), стоит понять: чьи это публикации и зачем собирается отчёт.

- Нормальный случай: организация отчитывается о собственной информационно-просветительской/PR-активности (свои посты, свой сотрудник, свой аккаунт) — обычная рутинная задача.
- Повод притормозить и спросить пользователя: похоже, что собирается исчерпывающее досье о публикациях частного лица третьей стороной без ясной легитимной цели — тогда лучше уточнить контекст (кто автор постов, для какой организации готовится отчёт, публичная ли это фигура) до того, как продолжать глубокий технический сбор.

## Типичные результаты/ограничения

- VK обычно удаётся закрыть почти полностью (90%+).
- Facebook: посты с характерным текстом закрываются поиском (3.1); посты только с фото/видео без текста и/или самые свежие/самые старые в диапазоне (out of Activity-Log reach из-за паджинации) могут остаться незакрытыми технически — это стоит явно проговорить пользователю как объективный предел инструментов, а не как незавершённую работу.
