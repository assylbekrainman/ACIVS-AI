## Шаг 0 — определи число сторон (2 или 3)

В Заявке разделе 2 сравни ФИО/БИН в п.8 «Заявитель» и п.9 «Грантополучатель».

- **Совпадают** → двухсторонняя структура (Заявитель-Победитель Конкурса и
  Грантополучатель — одно лицо, типично для вузов/НИИ, которые сами
  реализуют проект без отдельного ГП-ТОО). В проекте договора преамбула
  должна содержать одно лицо в двух ролях сразу. Часть пунктов эталона, где
  эти роли разделены (передача ОИС от Заявителя Грантополучателю, солидарная
  ответственность Заявителя за Грантополучателя), в этом случае становится
  юридически тавтологичной — это нормально для двухсторонней модели,
  отдельно фиксировать как ошибку не нужно.
- **Различаются** → трёхсторонняя структура, как в самом эталоне (типично:
  вуз/НИИ как Заявитель-Победитель + ТОО как отдельный Грантополучатель,
  реализующий коммерциализацию). В преамбуле оба лица должны быть перечислены
  через союз «и» — частый баг шаблона: дефис вместо «и» при копировании,
  проверяй это отдельно.

Число сторон определяет: количество экземпляров договора словами
(«в двух»/«в трёх» — должно соответствовать реальному числу сторон, а не
бездумно копироваться из трёхстороннего эталона) и то, нужна ли отдельная
проверка преамбулы на союз «и» (актуально только для 3 сторон).

## Порядок работы

### 1. Извлечение текста

Все документы большие (100+ страниц с приложениями, десятки листов в
смете). Не читай целиком через Read: выгружай в текстовые дампы через
`python-docx` (параграфы + таблицы отдельно, в файлы в scratchpad) и, если
смета отдельным файлом, `openpyxl` (data_only=True, по листам), затем читай
дампы кусками (`offset`/`limit`) — Read имеет лимит ~25000 токенов на вызов.

```python
import docx
def dump(fname, outpath):
    d = docx.Document(fname)
    with open(outpath, "w", encoding="utf-8") as f:
        for p in d.paragraphs:
            if p.text.strip():
                f.write(p.text.strip() + "\n")
        f.write("--- TABLES ---\n")
        for ti, table in enumerate(d.tables):
            f.write(f"Table {ti}:\n")
            for row in table.rows:
                f.write(" || ".join(c.text.strip().replace("\n"," / ") for c in row.cells) + "\n")
```

### 5. Безопасное редактирование docx

- Преамбулу, реквизиты, текстовые плейсхолдеры вне таблиц правь через unzip →
  `merge_runs.py` → точечная замена в `word/document.xml` → `validate.py`
  (см. общий скилл `docx`). **Важно:** при вставке многострочного текста в
  существующий `<w:t>` заменяй ВЕСЬ `<w:r>...</w:r>`, а не только внутренний
  `<w:t>` — иначе получится вложенный `<w:r>` внутри `<w:r>`, что ловит
  validate.py как ошибку схемы (`Element 'w:r' is not expected`).
- Табличные ячейки (KPI-таблицы, Приложение №4, колонка «Ответственный») —
  безопаснее и надёжнее через `python-docx`: найди строку по совпадению
  текста в первых 1-2 колонках, затем задавай `cell.text = value` (для
  простых значений) или собирай параграф из нескольких `run` (когда нужен
  курсив/жирный — см. оформление категорий KPI по эталону Kaz Hemp выше).
  Так не ошибёшься с индексом ячейки при сложных merged-заголовках.
- После КАЖДОГО этапа правок — `validate.py out.docx --original исходный.docx`
  (должно быть `All validations PASSED!`, разница параграфов = 0), затем
  рендер в PDF (`soffice.py --convert-to pdf` → `pdftoppm`) и визуальная
  проверка через Read на затронутых страницах — `pdftotext` не всегда находит
  текст в узких колонках (перенос по буквам), поэтому финальную проверку
  делай по картинке, а не по grep. Отдельно пересчитай числовые перекрёстные
  проверки (суммы по этапам = итог, грант+софинансирование = общий итог) и
  покажи это пользователю, а не только визуально проверяй текст.

3. **Прил.1 п.3 KPI**: нет символа `[●]` или другого незаполненного
   плейсхолдера; формат категорий/нумерации воспроизведён по эталону (см.
   Шаг 4). Уточни у пользователя, какой формат нужен, если не очевидно из
   предыдущей переписки.
4. **Статья НК РК** по освобождению от НДС — сверь с эталоном; если в
   драфте другая — не исправляй молча, спроси пользователя, какая верна для
   данного статуса налогоплательщика.
5. **Кол-во экземпляров договора**: `[трех]/[двух]` (или уже готовое число
   словами) должно соответствовать реальному числу сторон, определённому на
   Шаге 0, а не бездумно копироваться из трёхстороннего эталона.
6. **Раздел о расторжении (12.1.x)**: см. Шаг 2 — смещение нумерации при
   адаптации шаблона.
7. **Реквизиты Фонда** (ИИК/банк/БИК/адрес) — иногда в драфте по ошибке
   взяты из реквизитов другой стороны предыдущего/соседнего договора; сверяй
   с эталонным списком в Шаге 3, а не считай пустое поле единственным риском.
8. **Смета**: опечатки в столбце «Источник финансирования» (например,
   слитное «Градоговорнт» вместо «Грант» — известный баг мастер-шаблона, не
   вина конкретного менеджера, но стоит поправить при финализации) — пробегись
   по всей смете глазами; и пустая строка «Итого» (грант + софинансирование)
   в самом низу таблицы — её обычно забывают просуммировать.
