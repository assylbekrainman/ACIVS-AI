# Проверка и заполнение трёхстороннего Договора гранта РННТД по эталону Kaz Hemp

Эталон — Договор ТОО «Kaz Hemp» (№ ИРН DP32936258): трёхсторонний
(Фонд — Заявитель-Победитель Конкурса — Грантополучатель, три разных юрлица),
корректно и полностью заполненный по всем содержательным пунктам. Используется
как образец формулировок, лимитов, структуры и — отдельно — как источник

это всегда берётся из конкретного проекта (заявка, смета, протокол ННС).

Родственный скилл `dogovor-bilateral-fill` покрывает случай, когда
Заявитель-Победитель Конкурса и Грантополучатель — одно юрлицо (двухсторонний
формат, типично для вузов/НИИ, реализующих проект самостоятельно). Этот скилл —
для случая трёх РАЗНЫХ юрлиц (типично: вуз/НИИ как Заявитель-Победитель + ТОО
как отдельный Грантополучатель, реализующий коммерциализацию).

## Порядок работы

### Шаг 1 — Извлечение текста

Все документы большие (100+ страниц с приложениями, десятки листов в смете).
Не читай целиком через Read: выгружай в текстовые дампы через `python-docx`
(параграфы + таблицы отдельно) и `openpyxl` (data_only=True, по листам),
затем читай кусками (`offset`/`limit`).

```python
import docx
def dump(fname, outpath):
    d = docx.Document(fname)
    with open(outpath, "w", encoding="utf-8") as f:
        for p in d.paragraphs:
            if p.text.strip():
                f.write(p.text.strip() + "\n")
        f.write("--- TABLES ---\n")
        for ti, table in enumerate(d.tables):
            f.write(f"Table {ti}:\n")
            for row in table.rows:
                f.write(" || ".join(c.text.strip().replace("\n"," / ") for c in row.cells) + "\n")
```

### Шаг 2 — Постатейная сверка с эталоном (только по существу)

Пройди по преамбуле и всем разделам, игнорируя имена/БИН/суммы/даты (это
ожидаемо отличается), и раздели расхождения на три категории:

- **Ожидаемо отличается** — стороны, суммы, KPI, номер и название проекта,
  даты этапов.
- **Незаполненный плейсхолдер** — `[указать...]`, `[25/30/45]`,
  `[трех]/[двух]`, пустые ячейки таблиц, символ `[●]` вместо текста.
- **Существенное расхождение формулировки** — тот же по смыслу пункт
  сформулирован иначе, ссылается на другую статью НК РК, или содержит
  смещённую нумерацию перекрёстных ссылок. Не исправляй самостоятельно —
  сообщи пользователю оба варианта и предложи взять формулировку эталона,
  правь только после подтверждения.

### Чек-лист типичных ошибок (проверяй каждый раз)

1. **Преамбула**: союз «и» между Заявителем-Победителем и Грантополучателем
   не потерян при копировании шаблона (частый баг: дефис вместо «и»).
2. **Прил.1 п.2.2 Софинансирование**: `[25/30/45]%` заменено на конкретное
   число. Проверь арифметикой: итоговая сумма софинансирования / сумма
   гранта = процент; он должен совпасть с тем, что написано текстом.
3. **Прил.1 п.3 KPI**: нет символа `[●]` или другого незаполненного
   плейсхолдера. Формат — либо по этапам, либо по категориям (Технологические
   / Коммерческие / Социально-экономические KPI, как в Kaz Hemp — жирным
   названием категории, курсивом название показателя внутри буллета, только
   у ПЕРВОЙ категории проставлен номер `3.1`, у остальных ячейка номера
   пустая — так сделано в эталоне, воспроизводи один в один). Уточни у
   пользователя, какой формат нужен, если не очевидно из предыдущей переписки.
4. **Статья НК РК** по освобождению от НДС — сверь с эталоном (в Kaz Hemp это
   одна статья); если в драфте другая — не исправляй молча, спроси пользователя,
   какая верна для данного статуса налогоплательщика.
5. **Кол-во экземпляров договора**: `[трех]/[двух]` должно быть заменено на
   конкретное число словами.
6. **Раздел о расторжении (12.1.x)**: эталон исключает из общего правила
   возврата средств одно конкретное основание («отсутствие достаточных
   денежных средств для финансирования Проекта» — ГП в этом не виноват) и
   даёт для него мягкое последствие. При адаптации шаблона номер этого
   пункта часто сдвигается на 1 — проверяй по СМЫСЛУ основания, а не по
   номеру, скопированному из эталона.
7. **Реквизиты Фонда** (см. «Данные со стороны Фонда» ниже) — иногда в
   драфте перепутаны с реквизитами другой стороны.
8. **Смета**: опечатки в столбце «Источник финансирования» (например,
   слитное «Градоговорнт» вместо «Грант» — известный баг мастер-шаблона,
   не вина конкретного менеджера, но стоит поправить при финализации), и
   пустая строка «Итого» (грант + софинансирование) в самом низу таблицы —
   её обычно забывают просуммировать.

### Шаг 4 — Приложение №4 «Отчёт о реализации Проекта»: заполнение и сверка

Это самая частая точка ошибок. Правило: **каждая цифра плана должна иметь
прослеживаемый источник** — смета, экономический план заявки, или явное
допущение, озвученное пользователю.

| Строка Прил.4 | Источник | Как считать |
|---|---|---|
| Перечисление грантовых средств | Смета, лист «Свод», строка «Итого грант» | по годам как есть |
| Освоение средств софинансирования | Смета, лист «Свод», строка «Итого софинансирование» | по годам как есть |
| Заработная плата — всей команды | Смета, лист «1 ФОТ», строка «Итого» | по годам как есть |
| Заработная плата — в т.ч. учёным | Смета, лист «1 ФОТ» | сумма строк с должностями, содержащими «науч» (научный консультант, ВНС и т.п.) |
| Закуп основных средств | Смета, лист «2 Обор.» (или соотв.), строка «Итого» (грант+софинанс) | по годам как есть |
| Объём налоговых отчислений — всего/по гранту | Смета, лист «10 Налог», строка «Итого грант» | по годам как есть |
| Объём налоговых отчислений — от продаж | Смета обычно НЕ считает налог с будущей выручки отдельно | не бери случайную строку сметы (например, «НДС» другого этапа) под этот ярлык только потому что рядом стоит «-»; если нет отдельного расчёта — оставь пустым и скажи пользователю, что нужен отдельный расчёт от ГП |
| Охранный документ (патенты) | Смета, лист «7 ИС» (кол-во) + Приложение №2 Календарный план (в каком году патент фактически ПОЛУЧЕН, а не только подана заявка) | план ставь в год фактического получения, не подачи заявки |
| Лицензионное соглашение | Заявка, Раздел 5 п.24.3, Таблица E/F «Планируемый объём реализации» | бери построчно по годам как в заявке — эти цифры могут законно превышать регуляторный минимум KPI (п.2.1), это не ошибка |
| Количество видов продукции/услуг | Заявка, Раздел 5, Таблица E — считай, сколько видов продукции имеют ненулевое значение в данном году | |
| Объём реализуемой продукции — всего | Заявка, Раздел 5, Таблица F «Расчёт доходов», строка «Итого» по годам | НЕ подставляй регуляторный минимум KPI (15% от гранта) вместо реального прогноза — это разные числа, KPI это нижняя граница, а не план |
| — на внутренний рынок / на экспорт | Заявка, текст раздела 24.3 (описание клиентов/рынков) | если в явном виде не указано — раздели по best guess с пометкой допущения (например, все известные клиенты в РК → всё внутренний рынок, 0 экспорт) и явно скажи, что это допущение |
| Количество рабочих мест | Смета, лист «1 ФОТ» — число строк (сотрудников) | если состав группы не меняется по этапам — одно число на все годы |

**Важно**: если в заявке несколько источников выручки (например, услуга +
лицензия), проверяй КАЖДЫЙ отдельно и складывай, не путай отдельные строки
финансовой модели заявки с итоговыми строками сметы (смета считает расходы,
не доходы — доходы всегда идут из экономического плана).

Также проверь внутреннюю логику между Приложениями: если КПЭ (Прил.1 п.3)
говорит «не менее 1 договора», а Прил.4 показывает 5 — это не противоречие
(KPI — минимальный порог, Прил.4 — реалистичный план), но если наоборот
Прил.4 меньше порога KPI — это стоит подсветить пользователю.

### Шаг 5 — Безопасное редактирование docx

- Преамбулу, реквизиты, текстовые плейсхолдеры вне таблиц — точечно, сохраняя
  форматирование; при вставке текста в существующий `<w:r>` заменяй ВЕСЬ
  run, а не только `<w:t>` внутри него.
- Табличные ячейки (KPI, Приложение №4, «Ответственный» в календарном плане) —
  через `python-docx`: найди строку по совпадению текста в первых 1-2 колонках,
  затем задавай `cell.text = value` (для простых значений) или собирай
  параграф из нескольких `run` (когда нужен курсив/жирный — см. пример
  оформления категорий KPI по эталону Kaz Hemp: название категории `bold`,
  название показателя внутри буллета `italic`, остальной текст обычным
  шрифтом).
- После правок пересчитай числовые перекрёстные проверки (суммы по этапам =
  итог, грант+софинансирование = общий итог) и покажи это пользователю, а не
  только визуально проверяй текст.
